Product Requirements Document

CWM Daily Pulse

Author Vipasha Singla Updated October 2026 Status Draft Version 7.0
ProblemThe new sprint dashboard says a sprint is slipping, not why. And CWM offers List, Kanban and Gantt without telling users which one their current stage of work needs.
SolutionDaily Pulse (DP-1 to DP-5) explains, forecasts and offers fixes across modules. Stage-aware views (SV-1 to SV-5) detect the stage of work and open the right view, already set up.
Why CWMIt shares a database with the incidents, approvals and plans that cause slips, and already joins Project Workspace, EAP and Connected Work.
SuccessNorth star: % of SPM users whose first app open of the day is CWM. Kill signal: Pulse cause accuracy under 70%.

Jump to: Problem · Users · Goals · Solution · Requirements · AI principles · Not in scope · Journeys · Metrics · Non-functional · Dependencies · Risks · Open questions · Research

What changed in v7.0Requirements cut from eleven to ten, five per gap, renumbered DP-1–5 (Daily Pulse) and SV-1–5 (Stage-aware Views). Gap 02 is restated: CWM already has List, Kanban and Gantt; the problem is that users aren't told which one fits which stage. Every requirement now states why it needs AI rather than a query. The two-dashboard question is decided: the Pulse replaces the personal dashboard. Distribution signals and admin view-usage reporting are cut. The withdrawn "work too small for a board" problem is removed from the problem statement.
01 — Problem

Two gaps between opening CWM and knowing what to do.

GapUsers seeUsers needWhy CWM can't answer today
01JudgmentBurndown above the ideal lineWhich items caused it, why, and what to change before standupThe cause sits in other modules (ITSM, PPM, Project Workspace) and in free text: work notes, comments, incident descriptions
02GuidanceList, Kanban and Gantt with equal weight, plus a side panel of columns, lanes and groupingThe view that fits the current stage of work, already set upThe board knows its data but not the stage the team is in, so the choice and the setup fall to the user every time the stage changes
CostGap 01: ~15 minutes every morning across four modules to turn "something is off" into a decision. Gap 02: the wrong view hides what the stage needs (date conflicts don't show in Kanban, flow doesn't show in List), and each switch means reconfiguring.
Design constraint on every requirementA team of six gets something useful from a board within ten minutes without opening the settings panel.

04 — Solution

Two capabilities, one home screen.

01Daily Pulse

An AI morning briefing in My Work. It names what moved the sprint and why, finds blockers nobody linked, forecasts the landing, offers fixes, and lets the user act on each item in place.

02Stage-aware views

Each board is classified into one of four stages, and opens in the view that stage needs:

StageDefault viewStarting signals (day one)
PlanList: estimate, prioritise, assignNext sprint not started; items unestimated or unassigned
ExecuteKanban: flow, WIP, what's stuckSprint active
ScheduleGantt: sequence, dependencies, datesDates or dependencies edited in the last 48 hours, or a plan milestone within 10 days
ReviewBoard dashboardSprint ends within 2 days, or has ended
Where it lives — decidedMy Work → Daily Pulse. The Pulse replaces the personal work dashboard; it does not sit beside it. It is the first screen when a user opens CWM. Board → dashboard. The shipped sprint dashboard stays inside each board, unchanged, as one team's health view, and opens automatically in the Review stage. The Pulse links to it and never redraws its charts.
05 — Requirements

Ten requirements, five per gap.

Phase 1 (~1 quarter) explains what already happened, which users can verify. Phase 2 (~1–2 quarters) predicts and reaches across modules, and is gated on Phase 1 hitting its accuracy bar.

Phase column reads phase · priority. If capacity allows only one requirement, it is DP-1: it is the claim users can check, and nothing else in the Pulse is believed if it is wrong.

06 — AI principles

Rules every requirement follows.

PrincipleIn practice
If a query can do it, it isn't AICounts, filters and averages stay deterministic. AI is used only to read text, match by meaning, learn from history, or explain trade-offs.
Every claim shows its sourceEach Pulse item links the note, record or history it came from. Users can mark it wrong.
Suggest, never act aloneNo status change, link, reassignment or view lock happens without a user's click.
Respect existing accessTwo tiers. Everyone sees the impact ("blocked by an open incident, sprint ends Thursday"), derived server-side with no record data. The record and link show only to roles that already have access.
Fall back honestlyIf DP-1 cause accuracy drops below 70%, the Pulse shows the dashboard chart and says it can't explain this sprint yet.

12 — Risks

What could go wrong.

RiskLikelihoodMitigation
Cause tags are wrong and users stop trusting the PulseMediumSource shown on every item; mark-as-wrong feedback; 70% accuracy gate before Phase 2.
Unlinked-blocker suggestions are noisyMediumRequire shared CMDB service plus text match; propose, never auto-link; track accept rate.
Stage detection guesses wrong and users fight itMediumSuggestion only, one-click override, remembered. Override above one third pulls SV-2.
Two-tier disclosure rejected by platform governanceMediumValidate with a platform architect before DP-1 build. Fallback: reason only over records the user can see.
The Pulse reads as a second dashboardLowIt replaces the personal dashboard and links to board charts instead of redrawing them.
Scope drifts back toward configuration for enterprise asksHighThe ten-minute, no-settings-panel test gates each phase.
13 — Open questions

Still to resolve.

  1. DP-1 approach: an LLM reading notes per item, or a lighter classifier trained on tagged history? The LLM handles messy text better; the classifier is cheaper and easier to audit.
  2. Stage overlap: when a sprint is running and dates are being edited, which wins, Execute or Schedule? Current rule: Schedule for that session only.
  3. Empty Pulse: send a daily briefing even when nothing needs attention? Always-on builds habit; empty briefings erode trust.
  4. Scale: performance at 2,000+ connected items per user is unvalidated. Load test before Phase 2.
  5. Moat: if Atlassian's Teamwork Graph ingests ServiceNow data via marketplace apps, how much of DP-2's advantage remains?
14 — Research and validation

What this rests on, and what would falsify it.

SourceWhat it contributed

Escalation root-cause triageConfiguration divergence was the most common root cause. Evidence for Gap 02 and the no-settings-panel constraint.
Adjacent AI feature adoptionA sharp post-launch drop in another SPM product. Why trust is a kill signal here.
Secondary researchContext-switching cost (HBR 2022; Cornell/Qatalog); ClickUp reviews on "which view do I use for what"; competitive review of Monday.com, Asana, Atlassian, Linear, Notion.
Not yet validatedNo structured interviews yet. Plan: two weeks, no engineering time, 8–10 scrum masters and delivery leads at three CWM customers plus three teams that left for another tool. Gap 01: what did you do in the ten minutes after seeing the burndown off track, and where did you find the reason? Gap 02: which view do you plan in and which do you run standup in; when did you last change columns or lanes? Falsification: if leads say the dashboard is enough, or that they already use one view per stage without thinking, the investment moves to EAP integration and only SV-3 ships.
