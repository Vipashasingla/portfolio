What changed in v6.0Reframed around two gaps instead of three. Configuration is now stated as the larger problem, and its fix runs in two steps: FR-12 suggests the board setup in Phase 1 (rule-based, no usage history needed) and FR-9 learns the team's behaviour in Phase 2 and moves the surface with the work. 01 — Problem

The unique advantage is invisible.

CWM sits on the same platform as ITSM, HR, PPM, and EAP — the same database, same identity model, same infrastructure. No external work tool has that access. But CWM doesn't use it.

Today, SPM users start every morning by hopping between siloed ServiceNow modules that don't talk to each other:

Where they goWhat they checkWhat's missing
Email / SlackOvernight escalations, messages, FYIsNo priority. No connection to sprint status.
EAPSprint board — stories in progress, blocked itemsDoesn't show ITSM incidents or PPM approvals affecting the sprint.
ITSM moduleOpen incidents assigned to themNo link to sprint context or team impact.
PPM modulePending approvalsNo visibility into which tasks are blocked waiting on these approvals.
CWM dashboardSprint burndown, scope change, progress by statusSays the sprint is off track. Not which items moved the line, or what's blocking them outside this board.

All of this data lives in the same platform, the same database. But the user experiences it as five separate apps. The dashboard is a real step forward — it's now the reason a lead knows to start looking. It just can't answer the question that follows.

There is a second problem the modules don't explain. Roughly half of what fills a working day is too small for a board: chase the vendor, follow up after standup, read the doc by Thursday. CWM needs a board, a card and a state before it will accept an item, so that work goes to sticky notes, self-DMs and flagged email instead — outside the product entirely.

The invisible advantageConnected Work can already pull from any ServiceNow table — a structural advantage no outside tool can replicate. But today it shows up as rows in a board column, not as intelligence. The thing that makes CWM different from Asana or Monday.com is the thing CWM doesn't surface.
Cost15+ minutes daily turning "something is off" into "here's what I'm doing about it" — using context the platform already has. Plus a follow-up list that lives on paper.

03 — Solution

An AI morning briefing that reasons across every system.

Daily Pulse is an AI-generated morning briefing in CWM's My Space that reasons across every system on the Now Platform. The dashboard answers "how are we tracking." The Pulse answers the three questions that follow it, then lets the user act on the answer without leaving the page:

1. What matters right now

An AI-ranked priority list with cross-system reasoning. Not "your 12 assigned items" but "these 3 matter most — here's why." Item A unblocks 2 people. Item B's dependency resolved overnight. Item C is 3x over cycle time.

2. What changed that affects your plan

An overnight diff across all boards and connected records. Not "15 items moved state" but "the blocking incident was resolved at 11pm — you can pull the API story into sprint before standup." Cross-system cause and effect.

3. What's at risk before it's too late

Predictions, not reports. "Sprint at 120% of average velocity. Team B has an unresolved dependency from Team A. This item stuck 3x normal cycle time." Early warning, not a post-mortem.

4. Then: act where you stand

Each Pulse item carries its actions inline — nudge the owner, move the date, split or reassign, snooze until tomorrow. No navigation, no form. A briefing that only informs sends the user elsewhere to do the work, and they stay there.

And the surface itself arrives configured. The side panel that today asks which view, which columns and which lanes should open with those questions already answered for the work in front of the user (FR-12), so the board is useful before anyone has made a single setup decision.

Two surfaces, one workspaceMy Space hosts the Daily Pulse — it's why you open CWM (orientation). Team Boards are where work gets done (execution). The sprint dashboard sits inside the Pulse as the answer to "how are we tracking," not as a separate destination. Every insight deep-links to the board and item that needs attention.
04 — Why this surface

The platform should own the reasoning. CWM should own the morning.

The hardest objection is internal, not competitive: if reasoning across ITSM, HR, PPM and EAP is valuable, it belongs to a platform-level Now Assist surface every user gets — not to a work-management app with a few thousand monthly users. Half of that is correct.

ConcededThe intelligence should be built as platform capability — Now Assist skills, reusable by any consumer, owned by the platform AI team. This PRD does not propose a private AI stack inside CWM. The question is not who owns the reasoning; it is where a person receives it and where they act on it.
ReasonWhy it points to CWM
A briefing needs somewhere to landA platform-level briefing can say a sprint is at risk, then deep-link into five apps to act — the fragmentation it was meant to solve. CWM is the only SPM surface already holding boards, docs and tasks, so orientation and execution sit together.
CWM already holds the joinsIntegrations with Project Workspace (planned work) and EAP (sprint execution), plus Connected Work for records from any table. The insight comes from the join between planned, committed and ad-hoc work, and those edges already meet here. A new surface would rebuild them.
A quality bar you can hitPlatform-wide means every persona and module on day one, and reasoning accuracy is what kills this product. One audience, one set of joins, one accuracy target — expand after the predictions hold.
Information architecture — decided, not openTwo dashboards sitting as siblings force the user to choose which is theirs on every visit. My Work holds the Pulse — personal, cross-project, judgment. Board-level measurement moves inside the board as the answer to "how is this team tracking," and stops being a separate destination. One hierarchy of answers, one place to start.
Access — decided, not openZero configuration cannot mean bypassing ACLs or entitlements. Two-tier disclosure: a Pulse item states the fact and the impact ("blocked by an unresolved incident, sprint ends Thursday"), derived server-side, exposing no record data and requiring no source-table permission. The record and its deep link appear only for users whose existing role and entitlement already permit it; everyone else sees the impact and who to ask. To be validated with a platform architect before FR-1 is built.
05 — What's in scope

Eleven requirements, two gaps.

Design constraint on every requirement — the SMB testIf a team of six can't get something useful out of a board within ten minutes without opening the settings panel, it isn't done. Configuration here is not admin-gated — it is handed to the end user, who must pick the view, the columns, the kanban lanes, the grouping and the fields before the board is worth anything, and must revisit those choices every time the work changes phase. This constraint rules out any requirement whose first value depends on the user answering that panel, which is why FR-12 inverts it and why role-aware views were cut rather than deferred.

Delivered

CapabilityDetailStatus
D-1Sprint snapshot — a daily scheduled job capturing sprint state; the data foundation for every trend and prediction belowSHIPPED
D-2Sprint metrics — burndown against the ideal line, a scope-change view, and progress by status, derived from the snapshotSHIPPED

These were the expensive prerequisites and they are in the product. Everything below builds on the time series they create rather than duplicating the view they produce.

Phase 1 — Judgment and setup · ~1 quarter

IDRequirementPriority
FR-1Why the line moved — for any sprint tracking off its ideal line, name the items responsible and the reason each moved (added scope, stalled, or blocked by a connected record). The load-bearing requirement: if this is wrong, nothing else in Phase 1 is worth shippingP0
FR-2Ranked priorities with reasons — ranks the user's items by cross-system signals (due date, blocker status, dependency count, cycle-time deviation) and states why each mattersP0
FR-3Overnight diff — what changed since the user's last session (state, comments, reassignments, due dates) across boards and connected recordsP0
FR-4Act in place — inline actions on every Pulse item (nudge owner, move date, split, reassign, snooze) plus a deep link to the record, executed without leaving My SpaceP0
FR-12Suggested board setup — invert the configuration side panel from asking to proposing. A new board or sprint arrives with the view, columns and kanban lanes already set for the work about to be done; the panel remains available to change any of it, but answering it is no longer the price of a usable board. Rule-based on work type and sprint state, requiring no usage historyP0

Phase 2 — Cross-system reasoning · ~1–2 quarters

IDRequirementPriority
FR-6Cross-system impact alerts — surface when a connected record blocks or unblocks a sprint item (an incident, a pending approval, a Project Workspace plan change, or a cross-board dependency), with the downstream impact chainP0
FR-7Overload prediction — alert when committed work exceeds the team's historical delivery rate, using the snapshot time seriesP1
FR-8Follow-up resurfacing — commitments made from the Pulse (a nudge sent, a date moved, an item snoozed) reappear until closed or explicitly dropped, so nothing depends on the user rememberingP1
FR-9View intent — building on FR-12, learn from the team's actual usage and move the surface with the work: kanban while a sprint runs, list when the sprint is being assigned, card view during backlog grooming, timeline when a plan or quarter is in play, the Pulse otherwise. Suggested default only — one-click override, override remembered per user, and override rate instrumented as the health check on the phase modelP0
FR-10Distribution signals — at assignment time, surface how work has been distributed across recent sprints (repetition by item type or component, variety, and sequence given dependencies). Descriptive only: team-aggregate, opt-in at team level, visible only to the person accountable for the allocation. No per-person scores, no rankings, no recommended assigneesP1
FR-11View-usage reporting — show admins which views their teams actually open, by phase, over time, including views created and never opened againP1
Cut from the planRole-aware views, semantic search, AI status generation, the stale-item agent and the descope recommendation agent are removed, not deferred — each needs either configuration before first value or a level of trust in the reasoning that hasn't been earned, and they return only once FR-1 clears its accuracy bar. FR-5 quick capture is also cut, for a different reason: its problem statement was withdrawn in v6.0 and it returns only if user research evidences the need. Cost of what remains: roughly one quarter of CWM Core and Agile capacity, held against broadening Connected Work and net-new board features.
06 — What's NOT in scope

Deliberately deferred.

ItemWhy not now
Customizable Pulse layout / widget rearrangementUsers can't configure which insights appear or reorder the briefing. Ship the default experience first, validate what users engage with, then add personalization based on usage data.
Historical Pulse archive ("what did my briefing say last Tuesday?")Useful for retrospectives, but adds storage complexity. Defer until the daily-usage habit is established.
Team-level Pulse (aggregated briefing for a manager across reports)High value for PMs and directors, but requires role-hierarchy resolution and cross-board aggregation at scale. A Phase 2 dependency — build the individual Pulse first.
Slack / Teams delivery of the PulseUsers will want the briefing in their messaging tool, not just inside CWM. Defer until the in-app experience proves value — pushing to Slack before the content is trusted risks low engagement and a hard-to-recover first impression.
Natural-language "ask the Pulse" (conversational sprint queries)Compelling but expensive — requires real-time LLM inference per query. Ship the pre-computed daily briefing first; frequent ad-hoc questions would validate the investment.
Custom alert thresholds (e.g. alert only above 130%, not 110%)Configurability adds complexity before we know what thresholds work. Ship with sensible defaults, learn from accept/dismiss patterns, then open configuration.

09 — Research and validation

What this rests on, and what would falsify it.

SourceWhat it contributed
2.5 years building CWMFive core UI surfaces across four SPM teams, including sprint metrics and agile components.
50+ customer case tasksPPM and Project Workspace domain — customer problems in their own words, in writing.
Escalation root-cause triageAround a quarter traced to product behaviour diverging from user expectation rather than misconfiguration. Configuration divergence was the most common root cause — and because CWM's configuration is self-serve rather than admin-gated, that divergence is being produced by end users answering a settings panel they have no basis to answer. This is the evidence behind the zero-config constraint.
Adoption data, adjacent AI featureA sharp post-launch drop in another SPM product. Shipping an AI surface and having it used are different problems — the reason trust and accuracy are treated here as kill criteria rather than polish.
Secondary researchContext-switching cost (HBR 2022; Cornell/Qatalog) and competitive review across Monday.com, Asana, Atlassian, Linear, Notion.
A hypothesis this research withdrewAn earlier draft claimed that roughly half of a working day is too small for a board and therefore lives outside the product. No source supported it and it assumed a product limitation not verified against CWM. It was removed rather than defended, and the quick-capture requirement went with it.
Market evidence on views and configurationPublished ClickUp reviews documenting default views that go unopened and the "which view do I use for what" problem; Jira documentation confirming board view settings apply per user; Atlassian and Asana admin analytics reporting accounts and activity but never view-level usage; analyses of Linear's opinionated defaults, including a fifty-engineer team onboarding in an afternoon versus two to four weeks of Jira admin setup. Asana already auto-suggests assignees from workload and skill tags — capacity matching, not distribution fairness.
Not yet validatedNo structured interviews with delivery leads have been run. Before committing engineering: two weeks, no engineering time, 8–10 scrum masters and delivery leads across three customers already running sprints in CWM plus three teams that left for an external tool. Questions: what did you open first this morning and why; what did you do in the ten minutes after seeing the burndown off track; where do your untracked follow-ups live; when did you last configure something in CWM and who did it; what would make you stop paying for the other tool. Three more on the workspace: ask each lead to predict their most-used view before being shown the telemetry; ask which of the two dashboards they consider theirs; ask how they actually decide who gets which story today. Falsification: if leads say the dashboard is sufficient, or that they would rather act on the sprint inside EAP, the judgment layer is the wrong bet and the investment belongs in the Project Workspace and EAP integrations instead.

12 — Risks

What could go wrong.

RiskLikelihoodMitigation
AI ranking quality is poor — users ignore the PulseMediumShip with an accept/dismiss feedback loop. Measure accept rate weekly. Iterate before scaling.
Cross-system reasoning produces false positives (alert fatigue)MediumStart with high-confidence signals only (blocked, overdue). Expand gradually based on accuracy.
SPM users don't see a reason to open CWM over module-hoppingHighThe daily push notification creates the entry point. The Pulse shows cross-system value no individual module provides.
Engineering capacity split across 3 pluginsMediumP1 focuses on CWM Core + Agile. AI skills follow once the foundation is stable.
Proposed setup is wrong often enough that users distrust it and open the panel anywayMediumFR-12 is rule-based on work type and sprint state, which is a narrow and testable space. Accept rate is the metric; below roughly two thirds the rules are wrong and should be simplified rather than extended. The panel is never removed, so the downside is a wasted click, not a blocked user.
View intent guesses wrong and users fight it every morningMediumSuggestion only, one-click override, override remembered. Override rate above one third means the phase model is wrong and FR-9 is pulled. Failure here is cheap and reversible — a wrong view costs a click, unlike a wrong risk prediction, which costs trust.
Distribution signals are read as performance data about individualsHighTeam-aggregate by default, opt-in at team level, no per-person scores or rankings, no recommended assignees. Reviewed with HR and responsible-AI stakeholders before build, since the platform also runs HR. If it cannot ship descriptively, it does not ship.
Two-tier disclosure is rejected by platform governanceMediumValidate with a platform architect before FR-1 is built. Fallback: restrict Phase 1 reasoning to records the user can already see, accept a smaller zero-config surface, and report it honestly against the 60% target.
Requirements drift back toward configuration to satisfy enterprise asksHighThe SMB test gates each phase. Anything needing setup before first value ships as an optional refinement on a zero-config default, never as the default.
The Pulse reads as a second dashboard, confusing users about where to lookMediumThe dashboard is embedded in the Pulse as the "how are we tracking" answer rather than shipped as a rival surface. One destination, one hierarchy of answers.
13 — Open questions

Still to resolve.

  1. Ranking approach: weighted formula (due date × blocker × dependencies × cycle time) or LLM reasoning over full context? A formula is predictable and fast; an LLM is more nuanced but slower and harder to debug.
  2. Push notification threshold: send daily regardless, or only when there are actionable insights? Always-send builds the habit, but empty Pulses erode trust.
  3. Scale testing: the Pulse aggregates across boards. At 2000+ connected items per user, performance is unvalidated. Needs load testing before Phase 2.
  4. Suggestion granularity: should FR-12 propose a setup per board, or per team once and then apply it everywhere? Per board is more accurate and more repetitive; per team is one decision but wrong for any team running mixed work.
  5. Dashboard placement: should the shipped dashboard be embedded inside the Pulse, linked from it, or left standalone? Embedding makes the Pulse the single destination but risks a crowded first screen and rework on a surface that just shipped.
  6. Competitive moat: if Atlassian extends its Teamwork Graph to include ServiceNow data via marketplace integrations, the cross-system advantage weakens. Should CWM invest in platform-exclusive data sources (CMDB, financial plans, resource allocations) to maintain differentiation?
